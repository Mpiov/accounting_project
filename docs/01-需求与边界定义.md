# 子任务1：需求与边界定义（MVP）

版本：v1.0  
日期：2026-04-12  
适用阶段：0->1 产品落地（先 Android，后扩展）

## 1. 目标定义

构建一款“通知驱动的自动记账”应用：在用户授权前提下读取通知、在必要时完成通知界面截屏、提取交易信息、调用本地或云端模型完成结构化解析，并自动入账。

### 成功标准（MVP）

- 用户完成首次授权后，系统可自动识别主流支付通知并生成记账记录。
- 在无需用户逐条手工输入的情况下，自动入账准确率达到可用水平。
- 对低置信度记录提供“待确认”流程，避免误记账。

## 2. 目标用户与核心场景

### 目标用户

- 高频移动支付用户（微信支付、支付宝、银行卡短信提醒等）。
- 有持续记账需求但不愿手动录入的个人用户。

### 核心场景

- 收款/付款通知到达后，自动识别交易方向、金额、商户、渠道、时间。
- 通知文本信息不足时，触发通知面板截屏 + OCR 补齐字段。
- 自动分类入账；置信度低时进入待确认队列。

## 3. 核心流程（端到端）

1. 用户开启权限（通知读取、无障碍能力、截屏授权等）。
2. 系统监听通知并写入“原始事件池”。
3. 命中交易候选规则后执行解析：
4. 先做文本解析；不足时触发通知面板截屏并 OCR。
5. 构造结构化特征并路由到本地模型或云模型。
6. 返回标准交易对象（金额/币种/方向/商户/时间/渠道/置信度）。
7. 置信度 >= 阈值自动入账；否则进入待确认。
8. 用户纠错会反哺规则与模型提示词。

## 4. 范围定义

### 4.1 MVP 包含（In Scope）

- Android 10+（优先适配 Android 13/14/15 主流机型）。
- 通知来源首批：微信、支付宝、银行短信（按样本优先级迭代）。
- 数据对象：支出/收入两类基础流水。
- 账本能力：新增、编辑、删除、分类、搜索、按日/月统计。
- 解析能力：规则 + OCR + LLM 混合策略。
- 决策能力：自动入账 + 待确认复核。

### 4.2 MVP 不包含（Out of Scope）

- iOS 自动通知读取与同等自动化能力（仅保留后续评估）。
- 发票识别、对公报销流、多人协作账本。
- 跨设备实时协同编辑与复杂冲突解决。
- 全量银行 App SDK/直连网银交易拉取。

## 5. 功能需求（FR）

- FR-01：首次启动提供分步引导，逐项说明权限用途与风险。
- FR-02：通知监听服务可实时接收、去重、持久化通知事件。
- FR-03：支持交易候选检测（关键词、金额模式、来源白名单）。
- FR-04：在“信息不足”时可触发通知面板拉起并截屏。
- FR-05：截图预处理（裁剪、去噪）后 OCR 输出文本块。
- FR-06：交易抽取器输出标准字段：`amount direction merchant channel time order_id confidence raw_source`。
- FR-07：模型路由可在本地模型与云端模型之间切换。
- FR-08：高置信度自动入账，低置信度进入待确认队列。
- FR-09：待确认页支持一键确认、编辑、忽略、标记误报。
- FR-10：支持重复交易检测与合并提示。
- FR-11：提供基础分类（餐饮/交通/购物/转账/工资等）并可自定义。
- FR-12：支持离线记账查看（至少最近 3 个月数据可离线访问）。
- FR-13：支持日志与埋点（脱敏）用于准确率和稳定性评估。
- FR-14：支持“立即暂停自动记账”总开关。

## 6. 非功能需求（NFR）

- NFR-01（准确率）：首批渠道字段级准确率目标 >= 90%，金额字段 >= 98%。
- NFR-02（时延）：通知到入账 P95 <= 5 秒（仅文本路径）；截图+OCR 路径 P95 <= 12 秒。
- NFR-03（稳定性）：核心服务月崩溃率 < 0.5%。
- NFR-04（耗电）：后台日均额外耗电目标 < 5%（普通使用场景）。
- NFR-05（可恢复）：解析失败不丢事件，支持重试队列。
- NFR-06（可解释）：每条自动入账需可追溯来源（通知文本/OCR/模型版本）。

## 7. 平台与技术边界（必须遵守）

### 7.1 Android 系统能力边界

- 通知读取依赖 `NotificationListenerService`，并要求在清单中声明 `BIND_NOTIFICATION_LISTENER_SERVICE`。  
  参考：Android API 文档。
- 自动下拉通知栏依赖 `AccessibilityService.GLOBAL_ACTION_NOTIFICATIONS`。  
  参考：Android API 文档。
- 截屏依赖 `MediaProjection`，每次会话都要求用户同意；Android 14+ 重复复用 token 会抛 `SecurityException`。  
  参考：Android 官方行为变更与 Media Projection 文档。
- MediaProjection 会话要求前台服务（`FOREGROUND_SERVICE_MEDIA_PROJECTION`）与明显用户可感知状态。  
  参考：Android Media Projection 文档。

### 7.2 系统与生态限制

- 不能绕过其他 App 的 `FLAG_SECURE` 防截屏机制。
- 不同 ROM（尤其国产 ROM）对无障碍与后台保活策略差异大，需要单机型适配清单。
- 应用商店审核对“自动化/无障碍调用”较敏感，必须保留手动替代路径和清晰用途声明。

### 7.3 iOS 边界（当前阶段）

- iOS `UNUserNotificationCenter` 面向“本 App 的通知管理”，不提供与 Android 等价的第三方通知读取能力。  
  结论：iOS 在 MVP 阶段不承诺“全自动通知记账”同等能力，仅做后续能力评估。

## 8. 关键产品边界（防止范围失控）

- 默认“不强制自动化权限”：用户拒绝自动化权限时，仍可使用手动记账基础功能。
- 默认“先本地后云端”：有本地解析结果时，不上云。
- 默认“先保守后激进”：低置信度不自动入账。

## 9. MVP 验收标准

- 验收-01：从通知到自动入账全链路可在真机稳定跑通。
- 验收-02：至少 3 类来源（微信/支付宝/短信）在样本集上达到目标准确率。
- 验收-03：权限拒绝、系统回收、网络中断等异常路径可恢复且无数据丢失。
- 验收-04：每笔入账可追溯“数据来源 + 解析路径 + 置信度”。
- 验收-05：用户可一键关闭自动化能力并继续使用手动记账。

## 10. 当前假设（后续可调整）

- 先做中国大陆 Android 主流机型。
- 首版只做人民币（CNY）场景。
- 首版不接入海外云模型；如引入，按跨境规则单独立项。
