# 后端升级策略

版本：v1.0  
更新时间：2026-04-14  
适用范围：面向当前 Android 自动记账 MVP 的后端演进建议

## 1. 文档目标

当前项目已经有一条可运行的本地主链路：通知监听 -> 本地解析 -> 本地语义增强 / 本地 LLM -> 自动入账或待确认。  
因此后端升级不应该从“把所有逻辑搬上云”开始，而应该从“补齐本地链路现在最缺的支撑能力”开始。

这份文档的目标是回答三个问题：

1. 当前后端最值得补什么。
2. 后端应该按什么顺序升级。
3. 置信度与“未确认”流程在服务端应如何设计。

## 2. 当前现状

### 2.1 当前已经有的能力

- 客户端已经具备完整本地处理闭环。
- `core:network` 仍是云端分析占位接口，当前无真实生产后端。
- 已明确新的产品调整方向：
  - 通知自动记账链路不再把 OCR 作为默认处理层。
  - 图片导入记账链路单独存在，由用户主动触发。
- 数据主体都在端内：
  - 原始通知事件
  - 待确认记录
  - 正式账本记录
  - 设置项
  - 本地模型状态

### 2.2 当前真正缺失的后端价值

当前缺的不是“云端兜底接口”本身，而是下面这些支撑性能力：

- 规则与模型版本统一管理
- 用户纠错与样本回流机制
- 评测数据集与效果对比能力
- 可控的 AI 二次分析服务
- 备份 / 同步 / 导出闭环
- 运营与观测能力

## 3. 我认为最该补的后端逻辑

### 3.1 配置中心

后端应最先提供统一配置能力，而不是先做全量分析接口。

建议由后端管理：

- 可支持的通知来源列表
- 规则版本
- 关键词 / 正则热更新
- 本地模型目录与下载清单
- AI 复核开关与灰度策略
- 自动入账阈值与风控阈值

这样做的好处是：

- 不需要每次调规则都发新版 APK。
- 可以灰度验证不同策略的效果。
- 客户端仍能保持“本地优先”，后端只做控制平面。

### 3.2 样本回流与反馈闭环

当前客户端已经有“待确认”“确认”“忽略”“误报”这些动作。  
这些其实就是最有价值的监督数据，应该后端化管理。

后端建议新增：

- 用户确认后的标准样本存储
- 误报样本存储
- 规则命中轨迹存储
- 模型版本与结果的关联记录
- 可回放的评测样本集

后端价值在于：

- 让规则优化不再靠零散手工复盘。
- 让以后接真实云模型时可以量化效果。
- 为本地模型 prompt / schema 调优提供标准数据集。

### 3.3 AI 二次分析服务

相比“所有通知默认上云”，我更建议后端只提供一个“用户触发式 AI 复核服务”。

触发场景：

- 当前项不是高置信度
- 用户点击“AI 分析”按钮
- 或在待确认列表里批量发起 AI 复核

后端职责：

- 接收标准化候选与原始上下文
- 返回结构化字段修正建议
- 返回解释与证据摘要
- 返回是否建议自动确认

这样可以把云成本、合规风险和体验控制在一个合理范围内。

### 3.4 图片导入记账服务

我建议把“图片记账”作为一条独立于通知自动记账的后端能力来设计，而不是混进通知主链路。

建议支持的高优先级图片类型：

- 支付成功页截图
- 收款结果页截图
- 账单详情页截图

后续可扩展：

- 短信截图
- 聊天转账截图
- 小票 / 发票类图片

后端职责建议：

- 提供图片分析任务创建接口
- 识别图片类型
- 返回结构化记账建议
- 记录分析路径、模型版本和用户采纳结果

### 3.5 账本备份与同步

这是后端后续很重要，但不必最先上线的能力。

建议后端在中后期提供：

- 用户级账本备份
- 多设备同步
- 结构化导出任务
- 账户注销与全量删除

原因是：

- 当前单机可用已经成立。
- 同步是“体验升级”，不是“主链路补洞”。

### 3.6 观测与运营后台

当前项目后续一旦要稳定扩大使用范围，就需要一套后台观测能力。

建议至少有：

- 每条解析链路的成功 / 失败率
- 各来源命中率
- 待确认占比
- AI 复核触发率与采纳率
- 模型版本效果对比
- 误报率、重复率、漏记率

## 4. 推荐的后端分阶段升级路线

## 阶段 A：控制平面优先

目标：不改变客户端本地主链路，只补“可配置”和“可观测”能力。

建议先做：

- 配置中心
- 规则版本管理
- 本地模型目录清单接口
- 基础埋点与解析日志上报

阶段产出：

- 客户端仍以本地为主，但后端已经能调规则、发配置、做灰度。

## 阶段 B：反馈闭环与评测平台

目标：把“待确认”和“误报”变成真实可用的数据资产。

建议做：

- 待确认处理结果上报
- 样本标注表
- 评测数据集
- 效果对比看板

阶段产出：

- 后端开始真正提升解析能力，而不是只做存储。

## 阶段 C：AI 复核服务

目标：把云端能力定位成“用户触发式复核”，不是“默认云解析”。

建议做：

- `POST /review/analyze`
- `POST /review/confirm`
- `POST /review/feedback`
- 模型版本与解释结果持久化

阶段产出：

- 用户可以对未确认项发起 AI 二次分析。
- 后端可以沉淀“AI 复核到底有没有帮助”的数据。

## 阶段 D：账户与同步

目标：把单机账本升级成“可迁移、可备份、可同步”的服务。

建议做：

- 用户体系
- 账本备份
- 多端同步
- 导出中心
- 注销删除流程

## 5. 服务边界建议

我建议后端不要一开始就做成一个大而全的单体“智能记账服务”，而是按职责拆边界：

### 5.1 Config Service

负责：

- 功能开关
- 阈值
- 规则版本
- 模型目录
- 灰度配置

### 5.2 Review Service

负责：

- 未确认项 AI 复核
- 二次结构化分析
- 解释结果
- 用户采纳记录

### 5.3 Feedback Service

负责：

- 确认结果回流
- 误报回流
- 样本沉淀
- 标注集构建

### 5.4 Ledger Sync Service

负责：

- 备份
- 多端同步
- 导出任务
- 删除与注销

### 5.5 Observability Service

负责：

- 链路监控
- 指标聚合
- 效果对比
- 异常追踪

## 6. 关于你提出的“只区分高置信度 vs 未确认”

我整体上赞成，而且我觉得这比把“中 / 低置信度”直接暴露给用户更好。

### 6.1 为什么我赞成

- 用户不太关心“中还是低”，只关心“这笔能不能直接信”。
- UI 会更简单：
  - 高置信度：直接入账
  - 非高置信度：统一进入未确认
- 后续“AI 分析”按钮的心智也更清晰：
  - 这笔还不够确定，要么点 AI 复核，要么手动确认

### 6.2 为什么我不建议把中低置信度完全从系统内部删除

虽然前端可以只展示“未确认”，但系统内部仍然建议保留连续分数或内部等级。

原因是后端还需要这些信息做：

- AI 复核优先级排序
- 批量复核调度
- 效果评测
- 阈值调优
- 风险回放分析

也就是说：

- 对用户：只显示“高置信度 / 未确认”
- 对系统：继续保留原始 `score`

这是我最推荐的做法。

## 7. 针对“AI 分析按钮”的产品与后端建议

### 7.1 客户端交互建议

每条未确认项提供两个主动作：

- `AI 分析`
- `手动确认`

可选附加动作：

- `忽略`
- `标记误报`

### 7.2 后端接口建议

建议统一成幂等的复核任务接口：

- `POST /v1/review/tasks`
  - 创建 AI 复核任务
- `GET /v1/review/tasks/{id}`
  - 查询复核结果
- `POST /v1/review/tasks/{id}/feedback`
  - 提交用户是否采纳

### 7.3 返回结果建议

AI 复核结果不要只返回一句自然语言，而应返回结构化建议：

- 建议方向
- 建议金额
- 建议商户
- 建议分类
- 建议理由
- 证据片段
- 建议动作：`confirm` / `keep_pending`

## 8. 图片记账链路建议

这部分是对“用户主动上传图片记账”场景的正式建议。

### 8.1 产品规则

- 图片导入是用户主动触发行为，不属于后台自动记账。
- 无论走云端还是本地图片分析，结果都应进入“可编辑确认态”。
- 即使用户开启了云端分析、并且当前走的是云端多模态模型，也只生成建议，不允许自动入账。
- 用户始终可以修改金额、备注、分类、商户、时间等字段。

### 8.2 路由规则

建议链路固定为：

1. 用户上传图片
2. 如果用户已开启云端分析：
   - 直接走 `gemini-3.1-pro-preview`
   - 当前阶段先用 `gemini-3.1-pro-preview` mock 结果模拟
   - 结果返回后仍然要求用户手动确认
3. 如果用户未开启云端分析：
   - 先做 OCR
   - 如果本地轻量级模型已下载，则继续做本地模型分析
   - 如果本地模型未下载，则直接进入手动确认草稿
4. 最终统一进入可编辑确认界面

### 8.3 返回状态建议

为了让前端好展示，也让后端好观测，建议至少区分：

- `gemini_3_1_pro_preview_suggested`
- `ocr_plus_local_llm_suggested`
- `ocr_only_draft`
- `manual_confirmation_required`

其中前两类虽然已经有模型建议，但产品语义上仍属于“待用户确认”，不应视为自动入账成功。

### 8.4 为什么图片链路更适合多模态

相比 OCR 只识别文字，多模态模型还能理解：

- 页面版式
- 主金额位置
- 商户与金额的视觉关联
- 状态栏和装饰性噪音

因此对图片导入记账来说，多模态通常比“纯 OCR + 文本模型”更强。

### 8.5 为什么仍然保留 OCR + 本地模型路径

因为这条路径更适合：

- 用户没有开启云端分析
- 用户希望只在端侧处理
- 预算或后端能力还没完全到位的阶段

所以推荐把它作为“本地优先回退路径”，而不是删掉。

## 9. 我建议你现在就调整的一个决策

建议把当前产品规则明确成：

- `score >= 高置信度阈值`：自动入账
- 其他全部：进入未确认

同时保留：

- 原始 `score`
- `reason`
- `parsePath`
- `modelVersion`

这样你后面无论是加 AI 复核、后端样本回流，还是做效果分析，都不会丢信息。

## 10. 推荐的近期执行顺序

如果你近期准备开始做后端，我建议按下面顺序推进：

1. 先做配置中心与模型目录服务
2. 再做反馈回流与评测样本库
3. 然后做未确认项 AI 复核服务
4. 最后再做账本同步和备份

这是因为：

- 前三步能直接提升当前自动记账链路质量
- 同步与备份虽然重要，但不直接提升“识别对不对”

## 11. 一句话结论

当前后端最该补的，不是“把本地逻辑整体搬上云”，而是：

- 配置中心
- 反馈闭环
- AI 复核服务
- 评测与观测能力

而你提的“非高置信度统一归入未确认，再给 AI 分析或手动确认按钮”这个方向，我认为是对的，建议尽快采纳为产品层规则，同时把详细分数保留在系统内部。
