# 上线维护注意事项

本项目已经上线，后续任何改动都必须按线上项目处理。默认前提是：用户设备里可能已经有本地数据，服务器数据库里也已经有真实账号、会员、订单、账本、训练样本和模型版本。

## 总原则

- 不做破坏性修改，不随意删除字段、表、接口、配置项或历史数据。
- 不把“当前代码能跑”作为唯一标准，必须考虑已安装客户端、服务器已有数据和回滚路径。
- 涉及会员、订单、账本、待确认、通知原文、训练样本、模型版本的数据改动，必须先说明影响范围。
- 能用新增字段解决的问题，优先新增字段；确实需要改旧字段语义时，必须同步给出数据迁移和兼容方案。
- 线上配置优先走环境变量或后台配置，不把可运营的数值写死在业务代码里。

## 数据库变更

数据库改动必须先有迁移方案，再改代码。这里同时包含 Android 本地 Room 数据库和服务器 SQLite 数据库。

- 新增、删除、重命名表或字段前，必须先写明旧数据如何迁移、新数据如何回填、失败后如何回滚。
- Android Room 改 schema 时，必须提升数据库版本并提供显式 Migration，不能依赖清库、重装或 destructive migration。
- 服务器 SQLite 改 schema 时，必须提供可重复执行或带版本记录的迁移脚本，部署前先备份 `/opt/autobook/deploy/data/autobook.sqlite3` 或实际线上数据库文件。
- 不允许用临时 SQL 直接改线上核心数据，除非先备份、记录命令、说明影响范围。
- 统计字段、计数器、会员状态、订单状态等派生数据，如果新增维护逻辑，必须考虑事务一致性和异常重试。
- 数据迁移后需要验证关键查询：会员状态、订单列表、账单列表、待确认数量、训练样本列表、模型拉取。

## 后端接口

- 已有接口字段尽量保持向后兼容，新增字段应提供合理默认值。
- 修改响应字段含义前，必须检查客户端是否已经依赖该字段。
- 错误码要保持稳定，客户端已经使用的错误码不能随意改名。
- 会员、支付、自动记账体验次数、模型拉取等接口以服务器为权威，本地缓存只能做展示或短期兜底。
- 涉及访问令牌、刷新令牌、会员有效期的改动，必须考虑卸载重装、多设备登录和令牌过期场景。

## 客户端改动

- 本地账本、待确认项、设置项、会员状态缓存的结构变化必须配套 Room/DataStore 迁移。
- 不允许通过删除本地数据来规避兼容问题。
- 影响自动记账、待确认、手动记账、会员中心、支付页的改动，需要至少覆盖主路径手测。
- 免费体验次数、会员状态、模型权限等必须以服务器返回为准，客户端只做展示和调用门禁。

## 部署与回滚

- 部署前先确认当前分支、未提交改动、环境变量和目标服务器路径。
- 上线前至少完成本地编译或对应服务的最小自检；后端改动要跑 Python 编译或容器启动检查。
- 部署数据库迁移前必须备份数据库；备份文件名应包含日期时间。
- 每次部署后检查 `/health`、管理后台、会员状态接口、订单页和样本页。
- 改动如果涉及 Docker Compose 环境变量，必须确认服务器 `.env` 是否同步配置。
- 必须保留可回滚路径：旧镜像或旧代码、数据库备份、配置备份。

## 高风险区域

- 会员发放、会员有效期、订单确认收款。
- 自动记账体验次数扣减和自动记账总开关。
- 待确认数量、账本流水排序、分布式 ID。
- 通知原文上传、训练样本标签、模型发布和模型拉取。
- 登录、验证码、访问令牌刷新。

这些区域的修改不能只看单个页面效果，要同时验证客户端、服务器、后台管理页和已有数据。
