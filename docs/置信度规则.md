# 置信度规则（新方案提案）

版本：v0.1  
更新时间：2026-04-15  
适用范围：通知自动记账主链路  
状态：提案，可继续修改，不代表当前代码已完全实现

## 1. 目标

本方案用于替代当前旧的“简单来源基础分 + 少量关键词加分”规则，改为：

- 保留包名来源识别能力，并把它作为强先验。
- 不再把 `UNKNOWN` 来源在解析前直接过滤。
- 引入“来源先验 + 正文语义加分 + 风险扣分 + 高置信度门槛”组合评分。
- 兼容三类典型通知：
  - 微信 / 支付宝这类正文简短但来源可信的支付通知
  - 银行 App / 银行短信这类正文结构完整的动账通知
  - 零钱通利息、派息到账、收益到账等“已结算收益”通知
- 明确拦截“浮盈、估值、行情、资讯、营销”类不应自动入账的消息。

## 2. 核心原则

### 2.1 包名能力保留

包名识别能力必须保留，而且要做成可扩展规则表，而不是继续散落在 if / else 中硬编码。

原因：

- 微信、支付宝通知通常很简短，缺少账户、商户、时间等结构信息。
- 银行通知通常更完整，带尾号、账户、时间、币种、金额、动账提示。
- 同样一条“已支付￥0.01”，如果来源是微信支付官方通知，就应有更高可信度。

### 2.2 高置信度不等于字段完整

高置信度表示：

- 这是一条高概率真实交易通知。
- 金额和方向可信。

高置信度不表示：

- 商户、分类、对象、时间一定完整。

因此：

- 微信支付、支付宝这种“来源强可信 + 金额明确 + 方向明确”的简短通知，也可以直接高置信度。
- 银行类通知则更依赖账户、时间、动账提醒等结构化信息进一步加分。

### 2.3 UNKNOWN 不提前过滤

未知来源不应在解析前直接丢弃。  
应先解析正文，再根据语义结构决定：

- 进入高置信度
- 进入待确认
- 或过滤

说明：

- `UNKNOWN` 代表“包名先验不足”，不代表“通知本身不可信”。
- 只要正文语义足够强，`UNKNOWN` 也允许直接高置信度自动入账。
- `UNKNOWN` 只保留较低基础分，不再额外施加独立高置信度门槛。

## 3. 总体公式

```text
finalScore = sourcePrior
           + semanticBonus
           - riskPenalty
```

说明：

- `sourcePrior`：来源先验分，由包名规则表提供。
- `semanticBonus`：正文语义和结构化字段加分。
- `riskPenalty`：营销、资讯、方向冲突、无金额等风险扣分。

## 4. 来源先验分

来源识别建议抽象为规则表字段：

- `packagePatterns`
- `sourceClass`
- `channelLabel`
- `semanticProfile`
- `enabledByDefault`

### 4.1 来源类别与先验分

| 来源类别 | 说明 | 先验分 |
| --- | --- | --- |
| `TRUSTED_PAYMENT` | 微信支付、支付宝等原生支付通知来源 | `0.52` |
| `TRUSTED_BANK` | 银行 App、银行短信、动账通知来源 | `0.48` |
| `TRUSTED_FINANCE` | 零钱通、余额宝、券商、基金、理财类官方来源 | `0.34` |
| `UNKNOWN` | 包名未知或未在规则表中命中 | `0.25` |

### 4.2 建议的来源识别方向

- 微信支付：`com.tencent.mm`
- 支付宝：包含 `alipay`
- 银行 App：后续由规则表持续补充，例如建行、工行、农行、中行、招行等
- 银行短信：短信、消息类系统包
- 金融收益来源：零钱通、余额宝、券商、基金、理财等官方来源

说明：

- 本方案保留包名来源识别，但不把包名当成唯一判断依据。
- 未知来源也允许依靠正文语义进入中高置信度，甚至直接自动入账。

## 5. 正文语义加分规则

所有语义加分都按“组”计算。  
同一组内每一行最多加一次；同组不同行可以叠加，避免同一条规则被重复命中后无限加分。

### 5.1 金额组

| 命中条件 | 加分 |
| --- | --- |
| 明确金额且带币种，如 `￥0.01`、`人民币1.00元`、`RMB 1.00` | `+0.18` |
| 明确金额但只有 `1.00元` | `+0.14` |
| 只有裸金额数字，但看起来像钱 | `+0.06` |

### 5.2 方向组

| 命中条件 | 加分 |
| --- | --- |
| 明确收入方向：`收入`、`入账`、`到账`、`已到账`、`转入`、`收款` | `+0.18` |
| 明确支出方向：`支付`、`已支付`、`付款`、`扣款`、`消费`、`支出`、`转出` | `+0.18` |

### 5.3 账户结构组

| 命中条件 | 加分 |
| --- | --- |
| 命中尾号模式，如 `尾号1234` | `+0.14` |
| `储蓄账户`、`储蓄卡`、`借记卡`、`信用卡` | `+0.12` |
| `账户`、`银行卡`、`卡号` | `+0.08` |

### 5.4 时间组

| 命中条件 | 加分 |
| --- | --- |
| 可稳定提取出的明确时间，如 `4月15日22时23分`、`22:23`、`2026-04-15 22:23` | `+0.06` |

### 5.5 动账场景组

| 命中条件 | 加分 |
| --- | --- |
| `动账提醒`、`账户通知`、`交易`、`到账通知`、`入账通知`、`收款通知`、`余额变动` | `+0.10` |

### 5.6 对手方 / 商户组

| 命中条件 | 加分 |
| --- | --- |
| `商户`、`收款方`、`收款人`、`付款对象`、`交易对手` | `+0.04` |
| 真抽取到具体对象名 | `+0.02` |

### 5.7 币种组

| 命中条件 | 加分 |
| --- | --- |
| `人民币`、`RMB`、`CNY`、`￥`、`¥` | `+0.04` |

### 5.8 银行实体词组

| 命中条件 | 加分 |
| --- | --- |
| `建设银行`、`建行`、`工商银行`、`工行`、`农业银行`、`农行`、`中国银行`、`中行`、`招商银行`、`招行`、`交通银行`、`交行`、`邮储`、`浦发`、`平安银行`、`兴业银行`、`民生银行`、`华夏银行` | `+0.06` |

### 5.9 金融收益已结算组

| 命中条件 | 加分 |
| --- | --- |
| `利息到账`、`收益到账`、`派息到账`、`分红到账`、`赎回到账` | `+0.10` |

### 5.10 其它组

| 命中条件 | 加分 |
| --- | --- |
| `订单`、`您` | `+0.10` |

## 6. 风险扣分与上限封顶

### 6.1 收支方向冲突

如果同时命中收入词和支出词：

- 扣分：`-0.20`

### 6.2 没有可靠金额

如果没有稳定金额：

- 扣分：`-0.25`

### 6.3 营销 / 广告 / 资讯类消息

如果命中以下词语：

- `活动`
- `福利`
- `优惠`
- `推荐`
- `立即参与`
- `点击领取`
- `去看看`
- `广告`
- `资讯`

处理：

- 扣分：`-0.25`

### 6.4 资产估值 / 浮盈类消息

如果命中以下词语，但没有“到账、入账、卖出成交、赎回到账、派息到账”等已结算证据：

- `浮盈`
- `持仓收益`
- `净值估算`
- `市值`
- `涨跌幅`
- `收益率`
- `行情`

处理：

- 扣分：`-0.25`

### 6.5 UNKNOWN 来源处理原则

如果来源是 `UNKNOWN`：

- 不做“分数硬封顶到待确认”的限制
- 不做单独的高置信度附加门槛
- 只保留较低基础分 `0.30`
- 其余完全按统一的语义加分、风险扣分和分流阈值处理

## 7. 分流阈值

| 分数区间 | 结果 |
| --- | --- |
| `>= 0.86` | 高置信度，可自动入账 |
| `0.62 ~ 0.85` | 中置信度，进入待确认 |
| `< 0.62` | 低置信度，直接过滤 |

## 10. 示例

### 10.1 微信支付简短通知

通知：

`微信支付：已支付￥0.01`

预期：

- 来源先验高
- 金额明确
- 方向明确
- 已结算
- 直接高置信度

### 10.2 建行动账通知

通知：

`动账提醒：您尾号2134的储蓄账户4月15日22时23分收入人民币1.00元。点击查看>>`

预期：

- 银行来源先验
- 账户结构完整
- 时间明确
- 金额与币种明确
- 收入方向明确
- 即使有 `点击查看>>`，仍应高置信度

### 10.3 零钱通利息通知

通知：

`零钱通利息到账0.01元`

预期：

- 金融来源先验
- 已结算收益
- 金额明确
- 高置信度

### 10.4 股票浮盈消息

通知：

`今日持仓收益 +12.30 元`

预期：

- 命中资产估值 / 浮盈拦截规则
- 不自动入账
- 默认低置信度或最多待确认，取决于后续实现策略

### 10.5 未知来源但结构很强的通知

通知：

`您尾号2134的储蓄账户4月15日22时23分收入人民币1.00元`

前提：

- 包名未命中来源规则表

预期：

- 虽然来源先验低，但正文结构极强
- 金额、方向、时间、账户、币种信号完整
- 在没有任何 `UNKNOWN` 特殊限制的前提下，按统一规则计算后可以直接高置信度自动入账

## 11. 实现建议

建议后续按以下结构重构代码：

1. `SourceRuleTable`
   - 可扩展来源规则表
2. `NotificationSemanticFeatures`
   - 正文结构化特征抽取
3. `ConfidenceScorer`
   - 来源先验、语义加分、风险扣分统一计算
4. `ConfidenceGate`
   - 高置信度硬门槛检查

## 12. 文本剪裁规则

为保证实现简单、稳定且性能可控，通知正文统一只看前 `80` 个字。

### 12.1 归一化

- 标题与正文先合并成一段标准化文本。
- 统一做一次去空白、折叠连续空格、常见全角半角归一化。

### 12.2 评分窗口

- 统一只使用前 `80` 个字参与评分。
- 包括：
  - 关键词自动机匹配
  - 语义分组加分
  - 风险扣分
  - 结构化字段提取

用途说明：

- 大多数真实交易通知的关键信息都在前 80 个字内。
- 统一窗口可以避免规则分支过多，减少实现复杂度。

### 12.3 不建议的做法

以下做法不建议采用：

- 缺字段后再扩展扫描更多正文
- 对同一条通知使用多个不同长度窗口反复评分
- 每个关键词都对全文单独做一次扫描
- 不分阶段，所有通知一上来就全文重度解析

### 12.4 一句话结论

- 前 `80` 个字：统一评分窗口
- 超出前 `80` 个字的内容：默认不参与本轮置信度计算

## 13. 方案定位

本文件描述的是“新置信度方案提案”，不是旧规则总结。  
旧规则后续应逐步废弃，由本方案替代。
